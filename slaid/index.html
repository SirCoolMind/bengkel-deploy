Apa itu deployment dan penyelenggaraan?

Penyelenggaraan = maintenance

🚚

Deployment

Membawa kod dari laptop anda ke server, supaya pengguna boleh menggunakannya.

🔧

Penyelenggaraan

Memastikan ia terus berjalan: hidup semula bila mati, tahu apa yang rosak, kemas kini dengan selamat, kembali ke versi lama jika perlu.

Masalah biasa: "Di komputer saya boleh!" · deploy ikut ingatan · lupa satu langkah · tiada siapa tahu versi mana yang sedang berjalan.
  • Ask: "How do you deploy today?" Expect FTP, copying folders, remote desktop. No judgement: that's why we're here.
  • Keep talking while Codespaces build. Glance at the room: hands up = stuck on email codes.

Modul 1

PM2

"Pastikan API sentiasa hidup."

10:00 – 10:08Checkpoint 01
1

8 minutes. Keep it moving: one file, three commands, one demo.

PM2: process manager untuk Node.js

Masalah: npm run api mati bila terminal ditutup, atau bila ia rosak.

Keluar dari log: Ctrl + C (API terus berjalan)

  • The file is just "what to run, and what to do when it dies". Same command as json-server db.json --port 3000.
  • pm2 ls: point at status online and the ↺ restart column.
  • Ctrl+C in pm2 logs only stops watching the log, not the API. People always worry about this.

Cuba: matikan API dengan paksa

PM2 menghidupkannya semula dalam sesaat. Column ↺ = berapa kali ia telah dimulakan semula.

Maintenance dengan PM2:

pm2 logsApa yang berlaku?
pm2 restart inventori-apiSelepas kod baharu
pm2 startup + pm2 saveHidup sendiri selepas server di-restart
  • This is the "aha" of Module 1: the process came back by itself.
  • A high ↺ number in production = something is crashing repeatedly. Look at pm2 logs.
  • pm2 startup needs systemd, which Codespaces doesn't have; our Codespace uses pm2 resurrect on start instead. Just mention it.

  • Only three ideas: where the files are, where the API is, and "unknown page → index.html" so Vue can show it.
  • The trailing / in proxy_pass strips /api: /api/assets becomes /assets.
  • The app always calls /api/... (dev: Vite forwards it; server: Nginx forwards it), so the app code never changes between laptop and server.

Nginx, langkah demi langkah

Port 8080 → Open in Browser. Footer: Production
🧪 Cuba: pm2 stop inventori-api → refresh (F5) → 502 Bad Gateway. Nginx OK, API di belakangnya tidak. pm2 start inventori-api → pulih.
  • On a real server, steps 5 and reload are sudo systemctl start nginx / reload nginx. Codespaces has no systemd.
  • Always nginx -t before (re)loading: a typo would otherwise take the site down.
  • 502 = "Nginx couldn't reach the thing behind it". The most common error they'll see in real life. First place to look: pm2 ls, then /var/log/nginx/error.log.

Modul 3

Docker

"Bungkus semuanya, jalan di mana-mana."

10:20 – 10:45Checkpoint 03
3

25 minutes. Start the build early (it takes ~2 minutes the first time), and explain the files while it runs.

Tiga perkataan sahaja

📦

Image

Kotak yang sudah dibungkus: aplikasi + Node.js/Nginx + konfigurasi. Resipinya: Dockerfile.

▶️

Container

Kotak itu sedang berjalan. Satu image boleh menjadi banyak container.

🎼

Compose

Beberapa container dimulakan bersama dengan satu command. Senarainya: compose.yaml.

Kita build dua image: web (Nginx + aplikasi Vue) dan api (json-server). Sama seperti Modul 1 & 2, kini dalam kotak.
  • Analogy if needed: image = a frozen meal with instructions, container = the meal being eaten. Keep it short.
  • Tell them to run npm run checkpoint 03 and docker compose up -d --build now, so the first build runs while you explain the next two slides.

Dockerfile web: dua stage, sama seperti Modul 2

Stage 1 = npm run build dalam Modul 2
Stage 2 = salin dist/ + konfigurasi Nginx dalam Modul 2
Image akhir hanya Nginx + dist/ (~100 MB). Node.js dan node_modules ditinggalkan.

api.Dockerfile: Node + json-server, data dalam /data.

  • Read it as a recipe, top to bottom. Every line maps to something they typed in Module 2.
  • Why copy package*.json before the rest: Docker caches the slow npm ci step until the package list changes.
  • COMMIT_SHA feeds the footer. Locally it says "docker"; in Module 5 GitHub fills in the real commit.
  • docker.conf = the same Nginx config with three lines changed: listen 80, the root folder, and proxy_pass http://api:3000/.

compose.yaml: dua container, satu command

Port 9000 → Open in Browser. Footer: commit docker
  • The real file has a few more lines (healthcheck, restart policy, COMMIT_SHA). Show it in the editor if there's time.
  • Service names are hostnames: inside Docker, Nginx reaches the API at http://api:3000.
  • The API has no published port: only web can talk to it. Smaller attack surface.
  • docker compose ps: api shows (healthy) thanks to the HEALTHCHECK in api.Dockerfile.

Cuba: container dibuang, data kekal

Volume menyimpan db.json di luar container. Container baharu = data yang sama.
Kini deploy = satu command: docker compose up -d --build.
Seterusnya: biar GitHub yang menaipnya.
  • This is why deploys can replace containers freely: data lives in the volume, not the container.
  • docker compose down -v would delete the volume too. Don't run that one today.
  • Break next. Anyone whose build failed: docker compose logs, or catch up at the break with npm run checkpoint 03.

  • Vocabulary: workflow (the file) → job (a group of steps on one machine) → steps (commands).
  • Runner = the machine that runs a job. Today: GitHub's machine for testing, and in Module 5 our own.
  • "Clean machine" is the point: if it passes there, it doesn't depend on something only installed on my laptop.

Workflow pertama: .github/workflows/ci.yml

Repo anda di GitHub → tab Actions → klik run → klik Test & build → buka setiap step.
uses: = langkah siap guna (action) · run: = command terminal
  • Read it with the BILA / DI MANA / APA labels. Steps 3–5 are exactly what they'd type themselves.
  • npm ci vs npm install: ci installs exactly what's in package-lock.json, every time.
  • Wait for the first green tick together (~1 minute). Open the logs: every line of output is there.
  • If git push is refused with a message about "workflow" permission: create the file through the GitHub website instead (Add file → Create new file → .github/workflows/ci.yml → paste), then git pull in the Codespace. See the facilitator guide.

Cuba: pengurus mahu harga tanpa sen

  1. Ubah 2 → 0 (dua baris), simpan, commit, push.
  2. Tab Actions: ❌ merah. Buka step Test. Test mana yang gagal?
  3. Kembalikan kepada 2, commit, push → ✅ hijau.
Test menangkap perubahan sebelum ia sampai kepada pengguna. Jika perubahan itu memang dikehendaki, kemas kini test juga (tests/format.test.js).
  • Everyone does this. Reveal the log only after most people have a red X.
  • Point out the e-mail GitHub sends on failure, and the red X next to the commit on the repo's front page.
  • Reading CI logs is the real skill here: scroll to the first red line.
  • In Module 5 the deploy job has needs: test, so a red test means no deploy. That's the safety net.

  1. Repo anda → Settings → Actions → Runners → New self-hosted runner → Linux, x64
  2. Salin token sahaja (klik dua kali padanya) daripada baris ./config.sh --url … --token XXXXX
  3. Dalam terminal Codespace:
Kembali ke halaman Runners: status Idle 🟢
Jangan jalankan command lain di halaman GitHub itu. Skrip kita buat semuanya.
  • The runner only connects out to GitHub and asks for work. Nothing connects in. That's why this works for servers behind an office firewall, where GitHub can't SSH in.
  • The token is valid for one hour and can only register a runner. Still, don't paste it in a chat.
  • The script downloads the runner, registers it and starts it in the background. bash scripts/runner.sh status / log if anything looks wrong.

Job kedua: deploy selepas test lulus

Command yang sama seperti Modul 3. Bezanya: GitHub yang menaip.
  1. Ubah tajuk dalam src/App.vue (v-app-bar-title)
  2. git add -A && git commit -m "Tajuk baharu" && git push
  3. Tab Actions: ✅ Test & build → ✅ Deploy ke server
  4. Refresh port 9000: tajuk baharu, commit baharu 🎉
  • Three highlighted lines carry the whole idea: needs (only after tests), runs-on: self-hosted (on our server), and the Module 3 command.
  • --wait: the step only succeeds when the containers are up. The curl step is a smoke test: if the app doesn't answer, the run turns red.
  • Wait until the whole room has the new title. Then ask: "how many manual steps did you do on the server?" Zero.
  • Combine with the previous module: break a test and push. Deploy is skipped (grey), production stays on the last good version.

Penyelenggaraan (maintenance) dalam lima minit

↩️ Rosak selepas deploy?

git revert HEAD --no-edit + git push. CI/CD deploy semula versi sebelumnya.

🔍 Apa yang berlaku?

docker compose logs · pm2 logs · sejarah tab Actions: siapa deploy apa, bila.

♻️ Mati sendiri?

restart: unless-stopped (Docker) dan PM2 menghidupkannya semula. healthcheck memberitahu jika ia bermasalah.

⬆️ Kemas kini package?

Dependabot membuka pull request setiap minggu, CI men-test-nya. Cuba di rumah: CABARAN.md.

  • If there's time, do the revert live: git revert HEAD --no-edit && git push, then watch the old title come back.
  • Rollback through git means the history always shows what's running and why.
